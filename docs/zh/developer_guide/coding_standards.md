# 编码规范

## 代码风格

现有代码库可以作为格式约定的参考。以下提供了一些补充准则。

### 通用格式规则

以下规则适用于 **所有** 源文件（Rust、Python、Cython、shell 脚本等）：

- 只使用 **空格**，绝不使用硬制表符（tab）。
- 每行长度一般应保持在 **100 个字符** 以内；必要时进行合理换行。
- 优先使用美式英语拼写（`color`、`serialize`、`behavior`）。

### Shell 脚本的可移植性

本仓库中的 shell 脚本使用 **bash**（而非 POSIX sh），并且必须在 **Linux** 和 **macOS** 上都能移植运行。面向用户的脚本（例如 `scripts/cli/install.sh`）还必须能通过 Git Bash 或 WSL 在 **Windows** 上运行。

**Shebang**：始终使用 `#!/usr/bin/env bash` 以确保可移植性。

**常见陷阱**：GNU 和 BSD 工具在 Linux 和 macOS 上存在差异：

| 命令                  | Linux（GNU）        | macOS（BSD）       | 可移植方案                                |
|----------------------|-------------------|-------------------|------------------------------------------|
| `sed -i`             | `sed -i 's/…'`    | `sed -i '' 's/…'` | 使用备份扩展名：`sed -i.bak 's/…'`       |
| `stat`（文件大小）    | `stat -c%s file`  | `stat -f%z file`  | 通过 `stat --version` 检测              |
| `sha256sum`          | `sha256sum file`  | 不适用             | 使用 `shasum -a 256` 或做检测           |
| `readlink -f`        | 可用               | 不适用             | 避免使用，或改用 `realpath`             |
| `grep -P`（PCRE）    | 可用               | 不适用             | 改用 `-E`（扩展正则表达式）             |
| `date`（纳秒）       | `date +%N`        | 不适用             | 使用 `$RANDOM` 来避免缓存               |

**Bash 版本**：macOS 自带的是 bash 3.2；在面向用户的脚本中应避免使用 bash 4+ 的特性：

| 特性                               | Bash 版本要求 | 替代方案                          |
|-----------------------------------|--------------|----------------------------------|
| 关联数组（`declare -A`）           | 4.0+         | 使用文件或简单数组                |
| `readarray` / `mapfile`           | 4.0+         | 使用 `while read` 循环            |
| `${var,,}` / `${var^^}`（大小写）  | 4.0+         | 使用 `tr '[:upper:]' '[:lower:]'` |

**CI 脚本**（`scripts/ci/*`）运行在 Linux 环境上，因此在这些脚本中可以使用 bash 4+ 和 GNU 工具。

### 注释约定

1. 通常在每个注释块或文档字符串（docstring）之上留 **一个空行**，使其与代码在视觉上分开。
2. 使用 *句首字母大写*——首字母大写，其余保持小写，除非是专有名词或缩写。
3. 句号后不要使用两个空格。
4. **单行注释** *不得* 以句号结尾，*除非* 该行以 URL 或内嵌的 Markdown 链接结尾——在这种情况下，按链接要求原样保留标点符号。
5. **多行注释** 应使用逗号分隔句子（而不是每句一行加句号）。最后一行 *应当* 以句号结尾。
6. 注释保持简洁；重视清晰，只解释不易理解的部分——*简洁即是美*。
7. 文本中避免使用表情符号。

### 文档注释的语气

**Rust** 的文档注释应使用 **陈述语气（indicative mood）** 编写——例如，*"Returns a cached client."*（返回一个缓存的客户端）。

这一约定与 Rust 生态系统的主流风格保持一致，能让生成的文档对最终用户来说更自然。

### 术语与措辞

1. **错误信息**：避免在错误信息中使用 ", got"。根据上下文使用更具描述性的替代表达，如 ", was"、", received" 或 ", found"。
   - ❌ `"Expected string, got {type(value)}"`
   - ✅ `"Expected string, was {type(value)}"`

2. **拼写**：使用 "hardcoded"（一个单词）而不是 "hard-coded" 或 "hard coded"——这是更现代、更被接受的拼写方式。

3. **错误变量命名**：捕获的错误/异常使用单字母 `e`：
   - Rust：使用 `Err(e)` 而非 `Err(err)` 或 `Err(error)`，闭包中使用 `|e|` 而非 `|err|`
   - Python：使用 `except SomeError as e:` 而非 `as err:` 或 `as error:`

### 命名约定

1. **内部字段**：私有/内部字段可以使用缩写（例如 `_price_prec`、`_size_prec`）以保持热路径代码简洁。

2. **面向用户的 API**：公共属性、函数参数、返回类型以及指标名称/标签应使用完整、具描述性的名称（例如 `price_precision`、`size_precision`）。这样可以防止缩写术语泄漏到仪表盘或告警信息中。

3. **错误信息和日志**：为清晰起见使用完整单词（例如 "price precision" 而非 "price prec"）。用户不应看到任何缩写术语。

### 格式化

1. 对于较长的代码行，以及传入超过两三个参数时，应换行并对齐到下一个逻辑缩进层级（而不是试图在左括号之后做一种悬挂式的"美观对齐"）。这种做法可以节省右侧空间，让重要代码保持在视图中央，并且在函数/方法名变化时依然稳定。

2. 右括号应单独占一行，并对齐到逻辑缩进层级。

3. 多个悬挂参数或实参应以尾随逗号结尾：

```python
long_method_with_many_params(
    some_arg1,
    some_arg2,
    some_arg3,  # <-- trailing comma
)
```

## 提交信息

以下是关于提交信息风格的一些准则：

1. 主题行限制在 60 个字符以内。主题行首字母大写，且不以句号结尾。

2. 使用"祈使语气"，即消息应描述该提交应用后将会执行的动作。

3. 可选：使用正文来解释变更内容。与主题行之间用空行分隔。正文宽度保持在 100 个字符以内。可以使用带或不带句号的项目符号列表。

4. 可选：提供相关议题（issue）或工单的 `#` 引用。

5. 可选：提供任何有参考价值的超链接。

### Gitlint（可选）

Gitlint 可用于帮助自动执行提交信息规范。它会检查提交信息是否符合上述准则（字符数限制、格式等）。这是**可选启用**的功能，CI 中并不强制要求。

**优势**：鼓励编写简洁而清晰的提交信息，帮助形成对变更的清晰说明。

**安装**：首先在本地安装 gitlint：

```bash
uv pip install gitlint
```

要启用 gitlint 作为自动的 commit-msg 钩子：

```bash
prek install --hook-type commit-msg
```

**手动使用**：检查最近一次提交信息：

```bash
gitlint
```

配置文件位于仓库根目录的 `.gitlint`：

- **60 字符的标题限制**：确保在 GitHub 上清晰渲染，并在保持描述性的同时鼓励简洁。
- **79 字符的正文宽度**：与 Python 的 PEP 8 约定以及传统的 git 工具限制保持一致。

:::note
Gitlint 未来可能会在 CI 中强制执行，因此尽早采用这些实践有助于平滑过渡。
:::
