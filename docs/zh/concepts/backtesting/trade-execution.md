# 基于成交明细的执行

成交明细（trade tick）数据默认会触发订单成交（`trade_execution=True`）。一笔成交明细表明流动性已
在该成交价格处被吃掉，从而允许挂单中的限价单进行撮合。这与 K 线数据的默认行为
（`bar_execution=True`）相呼应。

希望将执行仅限于 L1 订单簿数据（报价或订单簿更新）的高级用户，可以禁用基于成交明细的执行：

```python
venue_config = BacktestVenueConfig(
    name="SIM",
    oms_type="NETTING",
    account_type="CASH",
    starting_balances=["100_000 USD"],
    trade_execution=False,  # 禁用基于成交明细的成交
)
```

当 `trade_execution=False` 或 `bar_execution=False` 时，相应类型的数据会跳过订单撮合和维护操作
（GTD 订单过期、追踪止损激活、金融工具到期检查）。报价（quote tick）始终会触发维护操作，因此在同时
使用多种数据类型时，这种设置通常是可以接受的。

撮合引擎使用一种“临时覆盖（transient override）”机制：在撮合过程中，它会临时将撮合核心的最优买价
（针对 BUYER 方向的成交）或最优卖价（针对 SELLER 方向的成交）调整到成交价格附近。这使得被动方
（passive side）的挂单能够跨越价差成交。请注意：底层订单簿数据永远不会被修改（它保持不可变），
只有撮合核心内部的价格参考会被调整。

**成交确定方式：**

当一笔成交明细触发订单撮合时，引擎按以下方式确定成交：

1. **订单簿反映该成交价格：** 若订单簿在该成交价格处存在流动性，则成交使用订单簿深度（标准行为）。
2. **订单簿未反映该成交价格：** 若订单簿的流动性处于不同价格，引擎会以订单的限价执行“成交驱动式
   成交（trade-driven fill）”，成交数量上限为 `min(order.leaves_qty, trade.size)`。

这确保了当一笔成交穿越价差、但订单簿尚未更新时，成交数量会被限制在该成交明细实际能够证明的范围内。
当 `liquidity_consumption=False`（默认）时，同一笔成交的数量可以在一次迭代中使多个订单成交。当
`liquidity_consumption=True` 时，消耗跟踪同样适用于成交驱动式成交：在有新数据到达之前，同一成交
价格处的重复成交会受到已消耗流动性的限制。

**恢复行为：**

撮合完成后，撮合核心的买/卖价只有在成交价格改善了它们（即使其远离价差）的情况下，才会恢复到原始
值：

- **SELLER 方向成交：** 只有当成交价格低于原始卖价时，卖价才会被恢复。
- **BUYER 方向成交：** 只有当成交价格高于原始买价时，买价才会被恢复。

若成交价格未能改善报价（例如一笔 SELLER 方向成交发生在卖价及以上），撮合核心会保留该成交价格。
这意味着在价差处或价差之外反复发生的成交，可能会逐步移动撮合核心的买/卖价。

**成交价格：**

- **在价格 P 处的 SELLER 方向成交：** 引擎会将撮合核心的最优卖价设为 P（前提是 P 低于当前卖价）。
  挂单价格在 P 或更高处的 BUY LIMIT（买入限价）订单将以其自身限价成交（若订单簿在该档位没有数据），
  或按订单簿价格成交（若订单簿有该档位数据）。
- **在价格 P 处的 BUYER 方向成交：** 引擎会将撮合核心的最优买价设为 P（前提是 P 高于当前买价）。
  挂单价格在 P 或更低处的 SELL LIMIT（卖出限价）订单将以其自身限价成交（若订单簿在该档位没有数据），
  或按订单簿价格成交（若订单簿有该档位数据）。

这种保守的处理方式确保了成交是以订单的限价而非可能更优的成交价格进行的。例如，一笔挂单价为
100.05 的 BUY LIMIT 订单被一笔在 100.00 处的 SELLER 方向成交触发时，会以 100.05 成交，而非
100.00。

:::tip
将成交明细数据与订单簿或报价数据结合使用可获得最佳效果：订单簿/报价数据用于确立基准价差，而成交
明细则用于触发那些可能位于价差之内、或领先于报价更新的订单执行。
:::

## 理解成交明细的主动方向（aggressor side）

成交明细上的 `aggressor_side`（主动方向）字段常常令人困惑：

- **SELLER 方向成交：** 表示一位卖方主动成交，卖入了买价。这为 **BUY**（买入）订单在该成交价格处
  提供了可成交流动性的证据。
- **BUYER 方向成交：** 表示一位买方主动成交，买走了卖价。这为 **SELL**（卖出）订单在该成交价格处
  提供了可成交流动性的证据。

换句话说，成交明细会触发主动方**对侧**订单的成交。一笔在 100.00 处的 SELLER 方向成交，可以成交你
挂在 100.00 处的 BUY LIMIT 订单，但不能成交你的 SELL LIMIT 订单，因为该成交本身已代表另一方在
卖出。

## 结合 L2 订单簿数据与成交明细

在同时使用 L2 订单簿数据（例如经过 100 毫秒节流的深度快照）和成交明细数据时：

1. **订单簿更新确立价差：** 每一次订单簿增量更新/快照都会更新撮合引擎对每个价格档位可用流动性的
   认知。

2. **成交明细提供执行证据：** 成交明细表明流动性已在某一特定价格处被吃掉，而这可能发生在两次订单簿
   快照之间。

3. **成交数量的确定：** 当一笔成交触发成交时：
   - 若订单簿已经反映了该成交价格处的流动性，成交使用订单簿深度
   - 若成交价格处于价差之内（不在当前订单簿中），成交数量上限为
     `min(order.leaves_qty, trade.size)`

4. **时间考量：** 在使用节流的订单簿数据（例如 100 毫秒）时，订单簿可能滞后于成交。发生在订单簿尚未
   反映的价格处的成交，会使用成交驱动式成交逻辑。

**常见误解：** 用户有时会以为每一笔成交明细都会触发成交。请记住：

- 只有主动方**对侧**的订单才可能成交。
- SELLER 方向成交 -> 可能触发 BUY 成交。
- BUYER 方向成交 -> 可能触发 SELL 成交。
- 订单簿的 UPDATE（更新）事件会移动市场，但只有在价格穿越你的订单时才会触发成交。

## 队列位置跟踪

当在启用 `trade_execution=True` 的同时启用 `queue_position=True` 时，撮合引擎会为限价单模拟队列
位置。这通过跟踪在某一价格档位有多少订单排在你的订单前面，实现更真实的成交行为。

**工作原理：**

1. **订单提交：** 当一笔 LIMIT（限价）订单被接受时，引擎会为该订单的价格档位记录当前同侧订单簿深度
   的快照，这代表排在该订单前面的数量。

2. **成交明细：** 当成交明细在该订单价格档位处发生时，“前方剩余数量（quantity ahead）”会被该笔
   成交的数量所扣减。只有正确方向的成交才会影响队列（BUYER 方向成交扣减 SELL 订单的队列，SELLER
   方向成交扣减 BUY 订单的队列）。带有 `NO_AGGRESSOR`（无主动方，常见于缺少主动方元数据的历史
   数据集）标记的成交会同时影响两侧。这种处理方式虽然偏保守，但可以防止订单无限期地停滞不前。

3. **成交资格：** 只有当“前方剩余数量”降为零时，该订单才具备成交资格。在使队列清空的那一笔成交中，
   只有超出队列前方数量的部分（成交数量减去前方剩余数量）可用于成交，从而防止过度成交。

4. **订单簿删除事件：**
   - L2（以及 L3 订单簿中聚合的 `F_MBP`/`F_TOB` 删除事件）：DELETE（删除）会移除整个价格档位，
     因此队列会被清空，该订单获得成交资格。
   - L3（MBO）：单个订单的 DELETE 会使队列按照该订单剩余的跟踪数量向前推进。已经被成交明细或
     聚合更新消耗过的订单不会被重复计数。

5. **订单簿更新事件：**
   - L2（以及 L3 订单簿中聚合的 `F_MBP`/`F_TOB` 更新事件）：UPDATE（更新）会将“前方剩余数量”
     限定在该档位新显示的数量之内。
   - L3（MBO）：单个订单的 UPDATE 会跟踪该订单数量的变化。数量减少会使队列按差值向前推进（时间
     优先级保留）；数量增加则会使该订单以更大的数量继续保持在队列前方；价格变化会将其从队列中
     移除。

6. **订单修改：** 价格变化会重置队列位置，该订单将以新的价格档位重新排到队列末尾。仅数量变化则会
   保留已累积的队列位置。

**配置：**

```python
from nautilus_trader.backtest.config import BacktestVenueConfig

venue_config = BacktestVenueConfig(
    name="SIM",
    oms_type="NETTING",
    account_type="MARGIN",
    starting_balances=["100_000 USD"],
    trade_execution=True,      # queue_position 生效的前提条件
    queue_position=True,       # 启用队列位置跟踪
)
```

**示例场景：**

1. 订单簿显示买价 100.00 处有 100 单位。
2. 你以 100.00 的价格提交一笔 BUY LIMIT 订单，数量 50 单位。前方剩余数量 = 100。
3. 一笔 80 单位的 SELLER 方向成交发生在 100.00 -> 前方剩余数量 = 20。尚未成交。
4. 一笔 30 单位的 SELLER 方向成交发生在 100.00 -> 队列清空，超出 10 单位。成交 10 单位。
5. 下一笔 50 单位的 SELLER 方向成交 -> 成交剩余的 40 单位。

**局限性：**

- 仅适用于 `LIMIT` 订单。止损限价单和触及限价单在此实现中不会被跟踪。
- 队列位置是按订单计算的，而非在同一价格档位的多个订单之间共享。
- 队列快照基于订单被接受时的订单簿状态。
- 带有 `NO_AGGRESSOR` 标记的成交会同时扣减两侧的队列，这可能会导致订单比实际情况更早成交（对队列
  估计而言偏保守，但能防止停滞）。

**L1 报价模式：**

在使用 `BookType.L1_MBP`（仅最优挂单报价）时，队列位置跟踪使用成交明细来扣减队列（与 L2/L3 相同的
机制），同时使用报价（quote tick）处理价格变化检测和延迟快照的解析。

- **成交明细：** 在订单价格档位处发生的成交会按成交数量扣减前方剩余数量，与 L2/L3 行为相同。只有
  正确主动方向的成交才会影响队列（SELLER 方向成交扣减 BUY 订单的队列，BUYER 方向成交扣减 SELL
  订单的队列）。
- **价格向远离方向移动：** 若买价跌破一笔 BUY 订单的价格（或卖价升破一笔 SELL 订单的价格），该
  订单的价格档位就被视为已被“穿越”，队列会清零，使该订单在下一笔匹配的成交中获得成交资格。
- **价格向靠近方向移动：** 若买价上升（或卖价下降），该订单价格所在档位并未被消耗，因此队列位置
  会被保留。
- **价格回到某一档位：** 当价格在离开后又回到该档位时，若之前的前方剩余数量大于新的显示数量，则
  会被限定在新的显示数量以内。
- **落后于最优买卖价的订单（待定）：** 当一笔限价单被放置在落后于最优买/卖价的位置（例如 BUY
  订单低于最优买价）时，由于 L1 数据在该价位没有可见深度，队列快照会被推迟。在最优买卖价到达该
  订单价格之前，成交会被阻止，届时会根据显示的数量对队列进行快照。待定订单在成交穿越其价格档位时
  也会被解析。

L1 模式使用相同的配置方式：设置 `queue_position=True` 并配合 `book_type=BookType.L1_MBP`。这为
仅有最优挂单报价可用的情况，提供了一种轻量级的替代方案，无需完整的 L2/L3 数据。

:::note
队列位置跟踪提供的是一种对队列动态的启发式模拟。真实交易所的队列行为取决于诸多无法从历史数据中
完美重建的因素（订单优先级规则、隐藏订单等）。
:::
