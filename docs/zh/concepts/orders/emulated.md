# 模拟订单（Emulated orders）

## 简介

即使你的交易场所原生不支持某些订单类型，模拟（Emulation）功能也能让你使用它们。

Nautilus 会在本地模拟这些订单类型（例如 `STOP_LIMIT` 或 `TRAILING_STOP` 订单）的行为，而在交易场所上实际执行时仅使用 `MARKET` 和 `LIMIT` 订单。

当你创建一笔模拟订单时，Nautilus 会持续跟踪一种特定类型的市场价格（由 `emulation_trigger` 参数指定），并根据你设置的订单类型和条件，
在触发条件满足时自动提交相应的基础订单（`MARKET` / `LIMIT`）。

例如，如果你创建一笔模拟的 `STOP_LIMIT` 订单，Nautilus 将监控市场价格，直至达到你的 `stop`（止损）价格，然后自动向交易场所提交一笔 `LIMIT` 订单。

为了执行模拟，Nautilus 需要知道应监控**哪种类型的市场价格**。默认情况下，它使用买卖报价（bid 和 ask 价格），
这也是为什么在示例中经常看到 `emulation_trigger=TriggerType.DEFAULT`（这等同于使用 `TriggerType.BID_ASK`）。
不过，Nautilus 还支持多种其他价格类型，用以指导模拟过程。

## 提交订单以供模拟

模拟订单唯一的要求是将 `TriggerType` 传给 `Order` 构造函数或 `OrderFactory` 创建方法的 `emulation_trigger` 参数。当前支持以下模拟触发类型：

- `NO_TRIGGER`：完全禁用本地模拟，订单被完全提交至交易场所。
- `DEFAULT`：与 `BID_ASK` 相同。
- `BID_ASK`：以报价（quotes）触发模拟。
- `LAST_PRICE`：以成交（trades）触发模拟。

所选的触发类型决定了订单模拟的行为方式：

- 对于 `STOP` 订单，触发价格将与指定的触发类型进行比较。
- 对于 `TRAILING_STOP` 订单，跟踪偏移量将基于指定的触发类型进行更新。
- 对于正在被模拟的 `LIMIT` 订单，限价将与指定的触发类型进行比较，以决定何时将订单作为 `MARKET` 订单释放。

以下是可设置到 `emulation_trigger` 参数中的所有可用值及其用途：

| 触发类型            | 说明                                                                                   | 常见用例                                                                            |
|:-------------------|:-----------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------|
| `NO_TRIGGER`        | 完全禁用模拟。订单被直接发送至交易场所，不进行任何本地处理。                              | 当你想使用交易场所的原生订单处理机制，或对于不需要模拟的简单订单类型。                 |
| `DEFAULT`            | 与 `BID_ASK` 相同。这是大多数模拟订单的标准选择。                                        | 当你希望使用“默认”类型的市场价格时进行通用模拟。                                       |
| `BID_ASK`            | 使用最优买价和卖价（报价）来指导模拟。                                                    | 止损单、跟踪止损单，以及其他应对当前市场价差做出反应的订单。                            |
| `LAST_PRICE`         | 使用最近一笔成交的价格来指导模拟。                                                        | 应基于实际成交而非报价触发的订单。                                                      |
| `DOUBLE_LAST`        | 使用连续两次最新成交价来确认触发条件。                                                    | 当你希望在触发前对价格变动进行额外确认时。                                              |
| `DOUBLE_BID_ASK`     | 使用连续两次买卖报价更新来确认触发条件。                                                  | 当你希望在触发前对报价变动进行额外确认时。                                              |
| `LAST_OR_BID_ASK`    | 基于最新成交价或买卖报价二者之一触发。                                                    | 当你希望对任何类型的价格变动都更加敏感响应时。                                          |
| `MID_POINT`          | 使用最优买价与卖价之间的中间点。                                                          | 应基于理论公允价格触发的订单。                                                          |
| `MARK_PRICE`         | 使用标记价格（衍生品市场中常见）来触发。                                                  | 尤其适用于期货和永续合约。                                                              |
| `INDEX_PRICE`        | 使用底层指数价格来触发。                                                                  | 当交易跟踪某一指数的衍生品时。                                                          |

## 技术细节

该平台使得在本地模拟大多数订单类型成为可能，无论该类型是否在交易场所受到支持。所有[环境上下文（environment contexts）](../architecture.md#environment-contexts)下的订单模拟逻辑和代码路径完全相同，并使用一个公共的 `OrderEmulator` 组件。

:::note
每个运行实例可拥有的模拟订单数量没有限制。
:::

## 生命周期

一笔模拟订单将经历以下几个阶段：

1. 通过 `submit_order` 方法由 `Strategy` 提交。
2. 发送至 `RiskEngine` 进行交易前风险检查（此时可能被拒绝）。
3. 发送至 `OrderEmulator`，在此处被*持有*/模拟。
4. 一旦触发，模拟订单将被转换为一笔 `MARKET` 或 `LIMIT` 订单并被释放（提交至交易场所）。
5. 被释放的订单在提交至交易场所前会经历最终的风险检查。

:::note
模拟订单与*普通*订单受到相同的风险控制约束，交易策略可以按正常方式对其进行修改和取消。它们在取消全部订单时也会被包含在内。
:::

:::info
模拟订单在其整个生命周期中都会保留原始的客户端订单 ID（client order ID），便于通过缓存（cache）进行查询。
:::

### 被持有的模拟订单

以下情况适用于当前被 `OrderEmulator` 组件*持有*的模拟订单：

- 原始的 `SubmitOrder` 命令将被缓存。
- 模拟订单将在一个本地 `MatchingCore` 组件内被处理。
- `OrderEmulator` 将订阅所需的任何行情数据（若尚未订阅），以更新撮合核心（matching core）。
- 模拟订单可以由交易者修改，并由市场更新，直至被*释放*或取消。

### 被释放的模拟订单

一旦行情数据到达触发/匹配了本地的模拟订单，将发生以下*释放（release）*操作：

- 该订单将通过一个额外的 `OrderInitialized` 事件被转换为 `MARKET` 或 `LIMIT` 订单（见下表）。
- 订单的 `emulation_trigger` 将被设为 `NONE`（此后任何组件都不再将其视为模拟订单）。
- 附加在原始 `SubmitOrder` 命令上的订单将被重新发送至 `RiskEngine` 进行额外检查，因为存在任何修改/更新。
- 若未被拒绝，该命令将继续传递至 `ExecutionEngine`，并照常通过 `ExecutionClient` 发送至交易场所。

## 可被模拟的订单类型

下表列出了哪些订单类型可以被模拟，以及在被释放提交至交易场所时它们会转换成哪种订单类型。

| 用于模拟的订单类型         | 可被模拟 | 释放后的类型  |
|:---------------------------|:---------|:--------------|
| `MARKET`                    |          | 不适用        |
| `MARKET_TO_LIMIT`           |          | 不适用        |
| `LIMIT`                     | ✓        | `MARKET`      |
| `STOP_MARKET`                | ✓        | `MARKET`      |
| `STOP_LIMIT`                 | ✓        | `LIMIT`       |
| `MARKET_IF_TOUCHED`          | ✓        | `MARKET`      |
| `LIMIT_IF_TOUCHED`           | ✓        | `LIMIT`       |
| `TRAILING_STOP_MARKET`       | ✓        | `MARKET`      |
| `TRAILING_STOP_LIMIT`        | ✓        | `LIMIT`       |

## 查询

在编写交易策略时，可能需要了解系统中模拟订单的状态。以下是查询模拟状态的几种方式：

### 通过缓存（Cache）

以下 `Cache` 方法可供使用：

- `self.cache.orders_emulated(...)`：返回所有当前正在模拟的订单。
- `self.cache.is_order_emulated(...)`：检查某个特定订单是否为模拟订单。
- `self.cache.orders_emulated_count(...)`：返回模拟订单的数量。

完整详情请参见 [API 参考](/docs/python-api-latest/cache.html)。

### 直接查询订单

你可以直接查询订单对象：

- `order.is_emulated`

如果该值返回 `False`，则说明该订单已从 `OrderEmulator` 中*释放*，因此不再被视为模拟订单（或从未是模拟订单）。

:::warning
不要保留对模拟订单的本地引用。当模拟订单被*释放*时，订单对象会发生转换。请改用 `Cache`。
:::

## 持久化与恢复

如果一个正在运行的系统在存在活跃模拟订单的情况下崩溃或关闭，那么这些订单将会从任何已配置的缓存数据库中重新加载到 `OrderEmulator` 内。
这可以在系统重启和恢复过程中保留订单状态。

## 最佳实践

在使用模拟订单时，请考虑以下最佳实践：

1. 始终使用 `Cache` 来查询或跟踪模拟订单，而不是存储本地引用。
2. 请注意，模拟订单在被释放时会转换为不同的类型。
3. 请记住，模拟订单在提交和释放时都会经历风险检查。

:::note
订单模拟功能使你即使在原生不支持高级订单类型的交易场所上，也能使用这些高级订单类型，从而使你的交易策略在不同交易场所之间更具可移植性。
:::
